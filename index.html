Scope

Far more than “update to .NET 10”

Moving the web host to .NET 10 does mean ASP.NET Core instead of System.Web. That still would not have extracted Muse as its own product, rebuilt the UI without Bootstrap/jQuery, or given developers an offline local stack. We did that work — .NET 10 is where it runs.

Product extraction Muse left the legacy monolith as its own repo and deployable — mlx.product.muse — rewritten from scratch, not a file-by-file port of the old solution.
New host & architecture ASP.NET Core, Razor Pages, CQS handlers, thin native endpoints, and architecture tests that block the old patterns from creeping back.
Front-end rebuild Bootstrap, Select2, jQuery, and friends removed. Same Muse look and interactions in owned CSS and TypeScript, guarded at build time.
Local stack reinvented Aspire AppHost, schema-as-code, Docker SQL, Mailpit — Muse runs offline without pointing developers at a billed Azure database.
Ops & observability OpenTelemetry, one support reference / operation_Id, Alpine containers, App Configuration, Key Vault, Sustainsys SAML on the modern host.
Quality bar for a rewrite More test C# than product code, architecture guards, web integration coverage, and Playwright E2E.

What replaced the removed libraries

Same selectors and interaction patterns where parity required it — implemented in Muse-owned CSS and TypeScript instead of vendor runtimes.

Select2 → native selects Custom multiselect / searchable filters in ClientScripts and Razor Pages — no .select2().
Bootstrap JS → native UI No .modal(), .collapse(), .dropdown(), or .tooltip() jQuery plugins.
Bootstrap CSS → design system Site.css + design-system / landing / home-shell tokens — not bootstrap.min.css.
jQuery UI datepicker → native Date inputs and Muse-owned date UX; datepicker CSS/JS left behind.
jQuery Ajax → fetch / ASP.NET Core TypeScript and server rendering replace $ / $.ajax on the host path.
Guardrail in CI/build Native UI guard fails the build if Select2, Bootstrap bundles, or jQuery patterns reappear.

Operations

Faster troubleshooting with one ID

End-to-end correlation is real on the rewritten host: one opaque trace ID ties the browser-visible support reference to Application Insights, nested CQS/SQL spans, and structured logs.

  1. User sees a reference Error pages and Problem Details show the originating Trace ID as the support reference.
  2. Response header Every HTTP response includes X-Muse-Trace-Id for network tools and support handoff.
  3. Find operation_Id That same value is Application Insights operation_Id — search once, pull the full request.
  4. Walk the chain Nested spans cover CQS commands/queries, SQL client calls, HTTP dependencies, and Snowflake work.

Front Door stays in the picture Incoming X-Azure-Ref is scoped with the Muse Trace ID (event 6311), so edge and app diagnostics can be joined when both are retained.

Alerts carry the ID Exception emails include the support reference / operation ID so on-call can jump straight into App Insights without guessing timestamps.

Local Aspire traces The same OpenTelemetry pipeline shows correlated request trees in the Aspire dashboard during development and load validation.

Privacy-safe by design The ID is opaque — not a user, patient, or client key — while request scopes keep path, method, renderer, and hashed actor context for triage.

Developer experience

Aspire made local Muse real

Framework Muse meant IIS Express, hand-wired SQL, and fragmented local setup. .NET 10 Muse runs through an Aspire AppHost — one composition for the stack developers need.

One command to boot the stack aspire start brings up the web host with SQL Server, App Configuration, Mailpit, Data Protection storage/Key Vault emulators, and optional legacy fallback.
Dashboard instead of guesswork Resource health, endpoints, logs, and OpenTelemetry traces in one place — including the same operation IDs support uses in production.
Surgical rebuild & restart aspire resource … rebuild|restart and aspire wait target a single service without killing the whole environment when binaries go stale.
Secrets stay out of the repo Generated SQL passwords, SystemWebAdapters keys, and local test credentials live in AppHost user-secrets — not checked-in config.
Schema as code — fully offline Legacy developers paid for a cloud Azure SQL database just to work locally. The AppHost now provisions SQL in Docker from repo scripts, applies migrations, and seeds SSO/test access — Muse boots with no Azure database and no VPN.
E2E and load in the same topology Playwright E2E and load-test resources hang off the AppHost so browser validation hits the real local stack, not a one-off machine setup.

Clone → restore → aspire start — the onboarding path the rewrite was designed around.
